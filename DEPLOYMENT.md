# Развёртывание в локальной сети

Портал устанавливается на один постоянно включённый сервер. Сотрудники открывают
его адрес в браузере; Python на их компьютерах не нужен. Системный администратор
выделяет постоянный IP и внутреннее DNS-имя, например `training.company.lan`.
Примеры ниже требуют замены имени на реальное. Настройки проекта автоматически
этой инструкцией не меняются.

## Интернет и Яндекс Формы

Локальное размещение портала не делает Яндекс Формы локальными: браузерам
сотрудников нужен доступ к сервисам Яндекса, ответы обрабатываются в Яндекс Формах.
В полностью изолированной сети потребуется собственный модуль тестирования.

Сейчас шаблоны также используют Tailwind CDN, Mammoth, JSZip, docx-preview и PDF.js
(включая worker). Для независимости портала от внешних CDN необходимо сохранить
библиотеки в `static/`, заменить ссылки и собрать Tailwind в локальный CSS.
Один `collectstatic` внешние зависимости не скачивает.

## Изменения в portal/portal/settings.py на сервере

Замените текущие значения следующими (остальные настройки сохраняются):

```python
import os

DEBUG = False
SECRET_KEY = os.environ['DJANGO_SECRET_KEY']
ALLOWED_HOSTS = ['training.company.lan']
CSRF_TRUSTED_ORIGINS = ['https://training.company.lan']
STATIC_ROOT = BASE_DIR / 'staticfiles'

# Для рабочего HTTPS-подключения:
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SECURE_SSL_REDIRECT = True
```

`ALLOWED_HOSTS` содержит имена/IP без протокола и порта, а
`CSRF_TRUSTED_ORIGINS` — полные доверенные адреса с протоколом и нестандартным
портом, если он есть. Для обычных запросов с того же origin дополнительный
список CSRF не обязателен. Не используйте `*` вместо конкретных адресов.

Создайте новый секрет, например командой
`python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"`,
и задайте его как постоянную переменную окружения службы `DJANGO_SECRET_KEY`.
Встроенный ключ из репозитория для рабочего сервера не используйте. `.env` текущий
проект автоматически не читает.

Если HTTPS завершается на обратном прокси, который сам устанавливает
`X-Forwarded-Proto`, добавьте:

```python
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
```

Прокси должен перезаписывать этот заголовок, а сервер приложения быть доступным
только с самого сервера. Иначе доверять заголовку нельзя. Сертификат внутреннего
удостоверяющего центра должен быть доверенным на компьютерах сотрудников.
Для временного HTTP-стенда три HTTPS-флага выше оставьте `False`, а адрес CSRF
задайте с `http://`; рабочие логины и пароли лучше передавать по HTTPS.

## Установка и запуск

1. Скопируйте проект на сервер и создайте новое виртуальное окружение совместимой
   версии Python. Существующее `venv` между машинами не переносите.
2. Установите зависимости: `python -m pip install -r portal/requirements.txt`.
3. Задайте серверные настройки и переменную секрета. Перейдите в каталог `portal`
   рядом с `manage.py`, затем выполните:

   ```text
   python manage.py migrate
   python manage.py collectstatic --noinput
   python manage.py createsuperuser
   python manage.py check --deploy
   ```

   Если база уже содержит администратора, создавать нового не требуется.
   В этом проекте доступ в панель определяется полем `role`, поэтому новому
   суперпользователю дополнительно назначьте роль через `python manage.py shell`:

   ```python
   from users.models import User
   User.objects.filter(username='ваш_логин').update(role='admin')
   ```

4. Запускайте приложение через сервер WSGI, а не `runserver`:

   - Windows: установите `waitress`, затем из каталога `portal` запустите
     `waitress-serve --listen=127.0.0.1:8000 portal.wsgi:application`.
   - Linux: установите `gunicorn`, затем из каталога `portal` запустите
     `gunicorn --bind 127.0.0.1:8000 portal.wsgi:application`.

   Закрепите выбранную версию сервера в серверном списке зависимостей.
5. Настройте nginx (Linux) или IIS с обратным прокси (Windows): HTTPS-запросы
   портала направлять на `127.0.0.1:8000`, сохранять исходный `Host`, передавать
   корректный `X-Forwarded-Proto`. `/static/` раздавать из `STATIC_ROOT`.
   Учтите размер и время загрузки MP4/PDF в лимитах прокси и WSGI-сервера.
6. **Не раздавайте `MEDIA_ROOT` публично.** Запросы файлов, включая `/media/`,
   должны проходить через Django: здесь проверяются вход и доступ к лекции.
7. Оформите WSGI-процесс как системную службу с автозапуском, постоянными
   переменными окружения, журналами и отдельной учётной записью.
   Ей нужны права записи в базу SQLite, её каталог и `media/`.
   Межсетевой экран должен разрешать доступ к HTTPS только из нужных подсетей
   компании; порт 8000 наружу не открывайте.
8. Проверьте с компьютера сотрудника вход, логотипы, материалы разных форматов,
   доступ по отделам, загрузку файлов администратором и отправку Яндекс Формы.

SQLite подходит для небольшого запуска с небольшой конкуренцией записи.
При росте нагрузки рассмотрите PostgreSQL; перенос существующих данных требует
отдельной миграции. Храните SQLite на локальном диске сервера, не на сетевой папке.
Настройте согласованные резервные копии базы и `media/`, проверьте восстановление.

## Оформление теста

Карточка вокруг iframe оформляется CSS портала. Стили вопросов, полей и кнопок
меняются в редакторе Яндекс Форм на вкладке «Тема»: CSS портала не может менять
содержимое iframe другого домена. Официальный `embed.js` сохранён для подстройки
высоты. Ссылки принимаются только по HTTPS на `forms.yandex.ru` и
`forms.yandex.com`, с путём `/u/идентификатор` или `/cloud/u/идентификатор`.
Сторонние ранее сохранённые ссылки не отображаются — замените их в редакторе лекции.
